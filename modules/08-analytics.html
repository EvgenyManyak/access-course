Цели обучения

В модуле 07 вы научились соединять таблицы и отбирать строки. Но аналитику редко нужны «сырые» строки: директор спрашивает «сколько?», «в каком месяце?», «по какой категории?», а бухгалтер просит «обновить прайс». Ответы на такие вопросы дают четыре инструмента Access, собранные в этом модуле: итоговые запросы с кнопкой Σ (SUM по группам), параметрические запросы (условие, которое спрашивает значение у пользователя), перекрёстные запросы (матрица «строки × столбцы») и action-запросы (UPDATE, INSERT, DELETE, SELECT INTO), которые меняют сами данные. По итогам модуля студент сможет:

  • строить итоговые запросы кнопкой «Итоги» (Σ) в конструкторе: GROUP BY, функции COUNT, SUM, AVG, MIN, MAX, округление ROUND до копеек и сортировка итогов по убыванию;
  • осознанно выбирать между WHERE (фильтр строк до группировки) и HAVING (фильтр групп после агрегации) и объяснять, почему условие «суммарная выручка больше 650» нельзя писать в WHERE;
  • делать запрос параметрическим: метки [Введите начальную дату] в критериях, явное объявление PARAMETERS … DateTime и ссылки на поля формы Forms!frm_Панель!НачальнаяДата;
  • создавать перекрёстные запросы мастером и типом «Перекрёстный» в конструкторе, читать и писать TRANSFORM … SELECT … GROUP BY … PIVOT, фиксировать столбцы через IN ("delivered","canceled","shipped");
  • безопасно выполнять action-запросы: копия данных через SELECT INTO, обновление цен UPDATE с соединением, добавление записей INSERT INTO … SELECT, удаление DELETE — с проверками «до/после», чтением предупреждения «Будет изменено N строк» и планом отката.

Необходимые предварительные знания

Модуль завершает блок «Запросы» и опирается на всё, что вы делали в модулях 06 и 07: без уверенной работы с сеткой QBE и без соединений четырёх таблиц ShopData двигаться дальше будет тяжело. Потребуется и математическая аккуратность: почти каждая цифра этого модуля проверяется вручную по мини-датасету, и мы будем сверять копейки. Если чувствуете пробел — потратьте полчаса на повторение, прежде чем начинать: итоговые и action-запросы прощают меньше, чем запросы на выборку.

  • из модуля 06 — конструктор запросов, сетка QBE, вычисляемые поля «Сумма: [UnitPrice]*[Quantity]», условия Between … And, In (…) и Is Null, свойство «Возврат»;
  • из модуля 07 — INNER JOIN нескольких таблиц, синтаксис Access SQL: даты в решётках #2018-01-01#, строки в двойных кавычках, псевдонимы AS;
  • из модулей 02–03 — структура ShopData: OrderDetails связывает Orders и Products, Products ссылается на Categories; каскадное удаление на связи Orders → OrderDetails включено (пригодится для DELETE);
  • из Excel — привычка к сводным таблицам: перекрёстный запрос Access устроен ровно как сводная «строки × столбцы × значения».
Важно

Action-запросы этого модуля физически изменяют данные базы. Все эксперименты с UPDATE и DELETE выполняйте в своей копии ShopData.accdb, а не в единственном экземпляре файла: копия делается через Проводник Windows за десять секунд и экономит вечер восстановления.

Теория

Итоговый запрос (aggregate query, totals query) — это запрос, в котором строки схлопываются в группы, а по каждой группе считается одно число. В конструкторе он включается кнопкой «Итоги» (Σ, вкладка Конструктор, группа Показать/Скрыть): в сетке QBE появляется строка «Групповая операция», где по умолчанию для каждого поля стоит «Группировка» (GROUP BY). Все поля с «Группировка» вместе задают ключ группы; поле, по которому считается итог, получает операцию Sum, Count, Avg, Min или Max. Access превращает это в SQL-конструкцию GROUP BY, и запрос возвращает ровно по одной строке на каждую группу — в этом его принципиальное отличие от обычного запроса, который возвращает по строке на каждую запись.

Набор агрегатных функций Access невелик, но покрывает нужды аналитика. Важно понимать, что SUM и AVG игнорируют NULL (пустые ячейки), а COUNT(*) считает все строки без исключений. Округление делается функцией ROUND(выражение, число знаков) — без неё деление средних значений даёт длинные хвосты вроде 275.0454545. Вот как функции ведут себя на мини-датасете ShopData:

Тонкость, на которой спотыкается каждый второй: WHERE и HAVING фильтруют на разных этапах. WHERE работает до группировки — он отсеивает исходные строки, поэтому агрегатов в нём ещё не существует. HAVING работает после группировки — он отсеивает уже посчитанные группы. Условие OrderStatus без canceled — это фильтр строки (WHERE), условие «суммарная выручка категории больше 650» — это фильтр группы (HAVING). Перепутать их дорого: попытка написать SUM(...) в WHERE даёт ошибку «Ваш запрос не включает указанное выражение ... как часть агрегатной функции», а условие по обычному полю в HAVING формально сработает, но читать и поддерживать такой запрос будет трудно.

Параметрический запрос — это запрос, критерий которого не «зашит», а спрашивается в момент запуска. Достаточно написать в строке «Условие отбора» текст в квадратных скобках — [Введите начальную дату] — и Access при каждом запуске покажет диалог с этим вопросом и подставит ответ в критерий. Метка должна быть одинаковой во всех местах, где используется один параметр: если в одном условии написано [Введите начальную дату], а в другом [начальная дата], Access задаст два разных вопроса. Явное объявление PARAMETERS в начале SQL фиксирует типы параметров и убирает гадание: PARAMETERS [Введите начальную дату] DateTime, [Введите конечную дату] DateTime;. Третий способ — вообще не спрашивать пользователя, а брать значения из формы панели аналитика: Forms!frm_Панель!НачальнаяДата. Такой ссылочный параметр нужен для отчётов и кнопок: пользователь один раз выбирает период на форме, а все запросы и отчёты молча его подхватывают.

Перекрёстный запрос (crosstab) — это сводная таблица внутри Access: строки одной размерности, столбцы другой, в ячейках агрегат. В SQL он описывается четырьмя ключевыми словами: TRANSFORM задаёт вычисление ячеек, SELECT — заголовки строк, GROUP BY — группировку строк, PIVOT — столбцы. Столбцы без IN(...) Access строит из фактических данных в алфавитном порядке и показывает только те, где есть значения; IN ("2018-01", "2018-02", ...) фиксирует состав и порядок столбцов, что критично для отчётов. Пустая ячейка перекрёстного запроса — это не ноль, а отсутствие строк (NULL): для замен на ноль используют Nz внутри TRANSFORM. Построить перекрёстный запрос можно двумя путями: мастером (Создание → Мастер запросов → Перекрёстные запросы), который работает ровно с одной таблицей или одним сохранённым запросом, и типом «Перекрёстный» в конструкторе, где доступны любые соединения.

Action-запросы меняют данные, а не показывают их — отсюда и особая дисциплина. Четыре типа: SELECT INTO создаёт новую таблицу из результата выборки (быстрый бэкап); UPDATE изменяет значения полей в существующих строках; INSERT INTO … SELECT добавляет строки из запроса-источника в существующую таблицу; DELETE удаляет строки (вместе с ними по каскаду уходят связанные записи). Перед каждым запуском Access показывает предупреждение с числом затронутых строк — формулировки вида «Будет изменено N строк» («Вы собираетесь обновить N запись(ей)»): это последний рубеж защиты, и цифру в нём нужно читать, а не механически нажимать «Да». Отменить выполненный action-запрос Ctrl+Z нельзя; единственная страховка — копия базы или копия таблицы, сделанная до запуска.

Пошаговая демонстрация

Соберём главный аналитический запрос модуля — qry_ВыручкаПоКатегориям: выручка каждой категории ShopData по позициям заказов, без отменённых заказов, с округлением до копеек и сортировкой по убыванию, а затем превратим его в параметрический: период будут задавать два диалога. Запрос соединяет четыре таблицы, поэтому перед началом убедитесь, что схема данных из модуля 03 на месте. Работаем в копии ShopData.accdb.

  1. На ленте откройте вкладку Создание и в группе Запросы нажмите Конструктор запросов. В окне Добавление таблицы последовательно добавьте таблицы Categories, Products, Orders, OrderDetails и закройте окно. Access сам нарисует линии связей по схеме данных.
  2. Двойным щелчком вынесите в сетку поле CategoryNameEn из Categories — это будет ключ группировки (английское имя категории, как в исходнике Olist).
  3. В первый свободный столбец строки «Поле» введите вычисляемое поле: Выручка: Round([UnitPrice]*[Quantity],2). Скобки вокруг имён полей обязательны — так Access понимает, что это поля, а не текст.
  4. На вкладке Конструктор в группе Показать/Скрыть нажмите кнопку Итоги (Σ). В сетке появилась строка «Групповая операция»: у CategoryNameEn — «Группировка», у Выручки — «Группировка». Поменяйте у Выручки значение на Sum.
  5. Вынесите в сетку поле OrderStatus из Orders. В строке «Групповая операция» выберите для него Условие (Where), снимите флажок Вывод на экран и в строке «Условие отбора» введите <>"canceled". Отмена — не выручка, и её надо выбросить до группировки.
  6. Нажмите Запуск (группа Результаты). Получите 5 строк. Сверьте с эталоном: bed_bath_table 769.50, computers_accessories 746.50, furniture_decor 640.00, health_beauty 631.50, automotivo 238.00.
  7. В строке «Сортировка» столбца CategoryNameEn пока ничего нет, а нам нужен топ по выручке. Выставьте столбцу «Выручка» сортировку по убыванию — категории выстроятся от 769.50 к 238.00.
  8. Теперь сделаем запрос параметрическим. Вынесите в сетку поле OrderDate из Orders, задайте ему «Групповая операция» = Условие, снимите флажок «Вывод на экран» и в строке «Условие отбора» введите Between [Введите начальную дату] And [Введите конечную дату].
  9. Объявите параметры явно: на вкладке Конструктор в группе Показать/Скрыть нажмите Параметры запроса. В открывшемся окне введите имя [Введите начальную дату] с типом Дата/время, затем [Введите конечную дату] с типом Дата/время. Имена должны совпасть с метками в критерии символ в символ.
  10. Нажмите Запуск: Access покажет два диалога по очереди. Введите 01.01.2018 и 31.12.2018 (в формате вашей локали). Результат — 4 строки: furniture_decor исчезла, потому что её единственная продажа (640.00) случилась в июне 2017-го. Сумма строк: 1230.90.
  11. Запустите запрос ещё раз с периодом 01.01.2017 — 31.12.2018: снова 5 строк и 3025.50. Один сохранённый запрос теперь отвечает на вопрос любого периода — это и есть смысл параметров.
  12. Сохраните запрос сочетанием Ctrl+S под именем qry_ВыручкаПоКатегориям и закройте. Он появится в области навигации в группе «Запросы» и станет источником отчёта в модуле 10.

Пример из работы аналитика

В понедельник утром директор вызывает вас с двумя поручениями. Первое: «Покажи по каждой категории, как шла выручка по месяцам 2018 года — мне нужна не простыня из 15 строк, а матрица, которую можно прочитать за минуту». Второе: «Поставщик автотоваров прислал новый прайс — подними цены категории automotivo на 5 процентов, но ничего не сломай: если ошибёшься, в отчётах будут неправильные цены». Обе задачи — будни аналитика в Access, и обе решаются запросами из этого модуля, без единой строчки VBA.

Для матрицы подходит перекрёстный запрос: строки — категории, столбцы — месяцы, полученные выражением FORMAT(OrderDate,"yyyy-mm"), в ячейках — SUM выручки без отменённых заказов. Столбцы мы жёстко зададим через IN ("2018-01", ..., "2018-06"), чтобы матрица всегда выглядела одинаково и не тасовала месяцы, а справа добавим столбец «Итого» по всем периодам — директор обязательно спросит «а всего?». Обратите внимание: «Итого» считает весь период 2017–2018, поэтому оно больше суммы шести месячных столбцов 2018 года — эти две цифры разные по определению, и это надо уметь объяснять.

Обновление цен — классический action-сценарий, и порядок действий здесь важнее самого SQL. Сначала проверочный SELECT покажет, что попадёт под условие (ровно один товар P-5001 «Насос для шин», 119.00). Затем SELECT INTO сделает копию Products в Products_Backup — наш план отката. Только после этого выполняется UPDATE с соединением на Categories и условием по имени категории, и Access перед запуском честно предупредит: «Вы собираетесь обновить 1 запись(и)». Финальные проверки: цена P-5001 равна 124.95, остальные семь цен не тронуты, сумма всех цен выросла с 1423.20 до 1429.15.

Что именно мы делаем в этом сценарии:

  1. Строим перекрёстный запрос qry_ВыручкаКатегорийПоМесяцам: TRANSFORM SUM, строки — CategoryNameEn, столбцы — месяцы 2018 через PIVOT … IN, значение — выручка без canceled.
  2. Добавляем в SELECT столбец «Итого» (SUM по всем периодам) и объясняем директору разницу между ним и суммой месячных столбцов.
  3. Выполняем проверочный SELECT: какие товары категории automotivo попадут под обновление (ожидаем один — P-5001, 119.00).
  4. Делаем копию таблицы: SELECT p.* INTO Products_Backup FROM Products — 8 записей в новую таблицу.
  5. Запускаем UPDATE с ROUND(...,2) и читаем предупреждение «Будет изменено 1 строка» — если бы цифра была другой, мы бы нажали «Нет» и разбирались.
  6. Проверяем результат: P-5001 = 124.95, сумма цен 1429.15; при ошибке откатываем UPDATE значениями из Products_Backup.
  7. По желанию (на копии базы) архивируем закрытые заказы 2017 года: SELECT INTO Orders_2017_Archive, затем INSERT INTO … SELECT для приостановленного O-10010 и DELETE для отменённого O-10006 — увидим, как каскадное удаление затрагивает OrderDetails.

SQL-код и разбор по строкам

Разберём три ключевых запроса модуля: параметрический итоговый, перекрёстный и связку action-запросов из сценария понедельника. Переключайтесь в режим SQL (правый щелчок по заголовку запроса → Режим SQL) и сравнивайте текст с тем, что сгенерирует Access: конструктор добавит лишние скобки вокруг условий — это нормально, смысл совпадает.

Запрос 1. Параметрический итоговый — тот самый qry_ВыручкаПоКатегориям из демонстрации:

PARAMETERS [Введите начальную дату] DateTime, [Введите конечную дату] DateTime;
SELECT c.CategoryNameEn,
       ROUND(SUM(od.UnitPrice * od.Quantity), 2) AS Выручка
FROM Categories AS c
INNER JOIN (Products AS p
            INNER JOIN (Orders AS o
                        INNER JOIN OrderDetails AS od
                        ON o.OrderID = od.OrderID)
            ON p.ProductID = od.ProductID)
ON c.CategoryID = p.CategoryID
WHERE o.OrderDate BETWEEN [Введите начальную дату] AND [Введите конечную дату]
  AND o.OrderStatus <> "canceled"
GROUP BY c.CategoryNameEn
ORDER BY SUM(od.UnitPrice * od.Quantity) DESC;
  1. PARAMETERS [Введите начальную дату] DateTime, [Введите конечную дату] DateTime; — объявляем оба параметра и их тип Дата/время; теперь Access не будет «угадывать» тип введённого значения, а имена меток зафиксированы документально.
  2. SELECT c.CategoryNameEn, — ключ группировки: одна строка результата на каждую категорию; псевдоним c сокращает длинные составные имена.
  3. ROUND(SUM(od.UnitPrice * od.Quantity), 2) AS Выручка — итог группы: сначала перемножаем цену на количество по каждой позиции, затем SUM складывает позиции категории, ROUND оставляет два знака; AS даёт столбцу понятное имя.
  4. FROM Categories AS c INNER JOIN (Products AS p INNER JOIN (Orders AS o INNER JOIN OrderDetails AS od ON o.OrderID = od.OrderID) ON p.ProductID = od.ProductID) — цепочка соединений изнутри наружу: позиции к заказам, товары к позициям; Access требует скобки при нескольких JOIN.
  5. ON c.CategoryID = p.CategoryID — замыкает цепочку: категории соединяются с товарами; без этого условия получили бы декартово произведение и завышенную выручку.
  6. WHERE o.OrderDate BETWEEN [Введите начальную дату] AND [Введите конечную дату] — фильтр строк по периоду; обе границы включаются, параметр подставляется в момент запуска из диалога.
  7. AND o.OrderStatus <> "canceled" — выбрасываем отменённые заказы до группировки; именно WHERE, потому что статус — свойство строки, а не группы.
  8. GROUP BY c.CategoryNameEn — собирает выжившие строки в группы по категории; все неагрегированные поля SELECT обязаны присутствовать здесь, иначе Access откажется выполнять запрос.
  9. ORDER BY SUM(od.UnitPrice * od.Quantity) DESC; — сортирует готовые группы по итоговой сумме по убыванию; в ORDER BY повторяется всё выражение агрегата, потому что псевдоним «Выручка» здесь использовать нельзя.

Мелкая тонкость: в сетке QBE удобнее писать вычисляемое поле как Round([UnitPrice]*[Quantity],2) и ставить над ним Sum — тогда Access сгенерирует SUM(Round(...,2)). На денежных значениях мини-датасета оба варианта дают идентичные копейки, потому что все цены уже двухзнаковые; для «грязных» данных из реальных прайсов выбирайте округление итога.

Запрос 2. Перекрёстный — матрица «категория × месяц 2018» из сценария (сохраните как qry_ВыручкаКатегорийПоМесяцам):

TRANSFORM SUM(od.UnitPrice * od.Quantity) AS Выручка
SELECT c.CategoryNameEn,
       SUM(od.UnitPrice * od.Quantity) AS Итого
FROM Categories AS c
INNER JOIN (Products AS p
            INNER JOIN (Orders AS o
                        INNER JOIN OrderDetails AS od
                        ON o.OrderID = od.OrderID)
            ON p.ProductID = od.ProductID)
ON c.CategoryID = p.CategoryID
WHERE o.OrderStatus <> "canceled"
GROUP BY c.CategoryNameEn
PIVOT FORMAT(o.OrderDate, "yyyy-mm")
  IN ("2018-01", "2018-02", "2018-03", "2018-04", "2018-05", "2018-06");
  1. TRANSFORM SUM(od.UnitPrice * od.Quantity) AS Выручка — чем заполняются ячейки матрицы: суммой выручки всех позиций, попавших в пересечение «категория × месяц».
  2. SELECT c.CategoryNameEn, SUM(...) AS Итого — заголовки строк плюс обычный агрегат как столбец-итог; «Итого» считается по всем периодам, а не только по шести месяцам из PIVOT.
  3. FROM ... INNER JOIN ... ON c.CategoryID = p.CategoryID — та же цепочка из четырёх таблиц, что и в первом запросе: перекрёстный запрос в конструкторе позволяет соединения, в отличие от мастера.
  4. WHERE o.OrderStatus <> "canceled" — без отменённых; строка O-10006 выбрасывается до любых агрегатов.
  5. GROUP BY c.CategoryNameEn — группировка строк матрицы; выражение-заголовок строки обязано попасть в GROUP BY.
  6. PIVOT FORMAT(o.OrderDate, "yyyy-mm") — столбцы: подпись месяца вида 2018-01; формат сортируется правильно, в отличие от названий месяцев.
  7. IN ("2018-01", ..., "2018-06") — фиксирует состав и порядок столбцов; без IN Access выстроил бы столбцы сам и включил бы 2017-е месяцы.

Запрос 3. Action-связка — копия и обновление цен из сценария (два отдельных сохранённых запроса, выполняются строго по порядку):

SELECT p.* INTO Products_Backup
FROM Products AS p;

UPDATE Products INNER JOIN Categories
ON Products.CategoryID = Categories.CategoryID
SET Products.UnitPrice = ROUND([Products].[UnitPrice] * 1.05, 2)
WHERE Categories.CategoryName = "automotivo";
  1. SELECT p.* INTO Products_Backup — создаёт новую таблицу Products_Backup со всеми столбцами Products; ключи и индексы при этом не переносятся, копия — это страховка значений, а не структуры.
  2. FROM Products AS p — источник копии: ровно 8 строк мини-датасета; Access предупредит «Вы собираетесь вставить 8 запис(ей) в новую таблицу».
  3. UPDATE Products INNER JOIN Categories ON Products.CategoryID = Categories.CategoryID — обновление с соединением: условие задано по имени категории, а не по «зашитому» числу CategoryID = 5, поэтому запрос переживёт переезд справочника.
  4. SET Products.UnitPrice = ROUND([Products].[UnitPrice] * 1.05, 2) — новая цена: старая умножается на 1.05 и округляется до копеек; ссылка Products.UnitPrice обязательна, потому что поле есть в обеих сторонах соединения.
  5. WHERE Categories.CategoryName = "automotivo" — скоуп обновления: одна строка (P-5001). Забытый WHERE обновил бы все 8 товаров.
  6. ; — перед выполнением Access покажет «Вы собираетесь обновить 1 запись(и)» (в англоязычной версии — сообщение вида «Будет изменено N строк»); цифра 1 здесь — контрольная: увидели 8 — жмите «Нет».

Вариант через конструктор запросов

Тот же перекрёстный запрос строится мышью двумя путями. Путь первый — мастер: быстрый, но работает ровно с одной таблицей или одним сохранённым запросом, поэтому для выручки категорий сначала пришлось бы сохранить запрос-источник. Начнём разминку на простой таблице Orders — посчитаем заказы по месяцам и статусам, это же основа задания I02.

  1. Откройте Создание → в группе Запросы нажмите Мастер запросов и выберите Перекрёстные запросы. В первом шаге выберите таблицу Orders и нажмите Далее.
  2. В списке «Доступные поля» выберите OrderDate как заголовок строки; мастер распознает поле даты и предложит интервал группировки — выберите по месяцам, затем Далее.
  3. Заголовком столбца назначьте OrderStatus и нажмите Далее. Именно этот шаг в мастере заменяет строку PIVOT.
  4. В ячейке матрицы выберите Count по полю OrderID, при желании включите флажок «Вычисления для каждой строки» — мастер добавит столбец с итогом по строке (в конструкторе такой столбец дописывают в SELECT как SUM). Нажмите Готово и сверьте: 12 строк месяцев, итоги — delivered 9, canceled 1, shipped 1, processing 1.
  5. Теперь путь второй — конструктор с соединениями. Создание → Конструктор запросов, добавьте таблицы Categories, Products, Orders, OrderDetails и закройте окно добавления.
  6. На вкладке Конструктор в группе Тип запроса нажмите Перекрёстный. В сетке QBE появится строка «Перекрестная таблица» со значениями «Заголовок строки», «Заголовок столбца», «Значение».
  7. Вынесите CategoryNameEn (строка «Перекрестная таблица» = Заголовок строки, «Групповая операция» = Группировка), затем вычисляемое поле Месяц: Format([OrderDate],"yyyy-mm") с тем же «Группировка» и значением Заголовок столбца, затем поле Выручка: [UnitPrice]*[Quantity] с «Групповая операция» = Sum и «Перекрестная таблица» = Значение.
  8. Чтобы ограничить столбцы шестью месяцами 2018-го, переключитесь в Режим SQL и допишите в PIVOT конструкцию IN ("2018-01","2018-02","2018-03","2018-04","2018-05","2018-06") — в сетке QBE списка IN для заголовков столбцов нет, а в столбец «Итого» превратите ещё одно поле Выручка: [UnitPrice]*[Quantity] с «Групповая операция» = Sum и пустой строкой «Перекрестная таблица».
  9. Вынесите OrderStatus, задайте «Групповая операция» = Условие, условие <>"canceled" и снимите флажок вывода. Нажмите Запуск, сверьте матрицу с разделом «Ожидаемый результат» и сохраните запрос как qry_ВыручкаКатегорийПоМесяцам.

Типичные ошибки

Типичная ошибка

Симптом: при запуске итогового запроса Access пишет «Ваш запрос не включает указанное выражение Sum(...) как часть агрегатной функции». Причина: в SELECT есть поле без «Группировка» и без агрегата — например, вынесли ProductName для красоты, но кнопку Σ не нажали или у поля осталась «Группировка» рядом с SUM в другом столбце без группировки. Лечение: нажмите «Итоги» (Σ) и каждому полю назначьте роль: ключ группы — «Группировка», итог — Sum/Count/Avg, вспомогательные поля — «Условие» со снятым флажком вывода.

Типичная ошибка

Симптом: условие «выручка больше 650» написано в строке «Условие отбора» — запрос не запускается или считает неправильно. Причина: WHERE фильтрует строки до группировки, когда суммы ещё не существуют; агрегаты доступны только после GROUP BY. Лечение: условия по итогам пишутся в строку «Условие отбора» под полем итога — в сетке QBE для поля «Выручка» должна стоять операция Sum, и условие автоматически попадёт в HAVING; в SQL — HAVING SUM(od.UnitPrice*od.Quantity) > 650.

Типичная ошибка

Симптом: вместо двух диалогов Access задаёт три-четыре, или запрос возвращает пустую таблицу при очевидно заполненном периоде. Причина: имена параметров различаются хоть на один символ ([Введите начальную дату] и [Начальная дата]) — Access считает их разными; либо PARAMETERS не объявлен, и введённый текст даты приводится к типу неудачно. Лечение: копируйте метку через Ctrl+C, объявите параметры в окне «Параметры запроса» с типом Дата/время и сверьте, что в SQL каждая метка встречается столько раз, сколько условий её использует.

Типичная ошибка

Симптом: после UPDATE «поднять цены automotivo на 5%» изменились все 8 товаров, а P-5001 показывает 131.20 вместо 124.95. Причина: первый запуск был без WHERE — умножились все цены; второй запуск с WHERE умножил уже обновлённую цену: 119.00 → 124.95 → 131.20. Лечение: перед каждым action-запросом делайте проверочный SELECT с тем же условием и читайте предупреждение «Будет изменено N строк»; здесь цифра должна быть 1. Для отката используйте Products_Backup (SQL в эталонном решении).

Типичная ошибка

Симптом: повторный запуск SELECT p.* INTO Products_Backup падает с ошибкой «Таблица "Products_Backup" уже существует». Причина: SELECT INTO не дозаписывает данные и не пересоздаёт таблицу — при существующем имени он отказывается работать. Лечение: перед повторным созданием копии удаляйте старую (в области навигации правый щелчок → Удалить) или используйте INSERT INTO … SELECT, если структура уже готова и дозапись допустима.

Типичная ошибка

Симптом: мастер перекрёстных запросов не даёт добавить вторую таблицу, а матрица по CategoryNameEn вообще не собирается. Причина: мастер принимает ровно одну таблицу или один сохранённый запрос, а категория живёт в Categories, выручка — в OrderDetails. Лечение: либо сначала сохраните запрос-источник с соединениями (четыре таблицы и нужные поля без агрегата), либо стройте перекрёстный запрос конструктором: вкладка «Конструктор» → группа «Тип запроса» → «Перекрёстный».

Практический совет

Практический совет

Для ежедневных отчётов выносите параметры на форму-панель: в критерии пишите Forms!frm_Панель!НачальнаяДата и Forms!frm_Панель!КонечнаяДата, а в окне «Параметры запроса» объявите оба с типом Дата/время. Практический совет

Для осей времени используйте FORMAT(OrderDate,"yyyy-mm"): такие подписи сортируются хронологически, потому что «2018-01» меньше «2018-06» как текст. Названия месяцев FORMAT(OrderDate,"mmmm") красивы, но сортируются по алфавиту («апрель» перед «март»); если нужны оба варианта — держите сортируемый столбец-ключ и подпись отдельными полями.

Практический совет

Двойной щелчок по action-запросу в области навигации не выполняет его, а показывает предпросмотр — таблицу строк, которые будут затронуты. Это бесплатный последний рубеж проверки: перед запуском посмотрите предпросмотр, затем запустите кнопкой с восклицательным знаком и сверьте число в предупреждении «Будет изменено N строк» с ожидаемым.

I01. Выручка по категориям

Цель: построить сохранённый запрос qry_ВыручкаПоКатегориям — выручка каждой категории ShopData по позициям заказов без отменённых, с округлением до копеек и сортировкой по убыванию — и научиться проверять агрегаты разложением по строкам мини-датасета.

Исходные таблицы: Categories (5 категорий), Products (8 товаров), Orders (12 заказов), OrderDetails (15 позиций).

Используемые поля: Categories.CategoryNameEn, Products.CategoryID, Products.ProductID, Orders.OrderID, Orders.OrderStatus, OrderDetails.Quantity, OrderDetails.UnitPrice; вычисляемое «Выручка: [UnitPrice]*[Quantity]».

Пошаговый план:

  1. Создайте запрос в конструкторе и добавьте четыре таблицы; проверьте, что Access нарисовал все три линии связи.
  2. Вынесите CategoryNameEn и введите вычисляемое поле «Выручка: Round([UnitPrice]*[Quantity],2)».
  3. Нажмите «Итоги» (Σ): CategoryNameEn — «Группировка», Выручка — Sum.
  4. Вынесите OrderStatus с операцией «Условие», условие без canceled, флажок вывода снимите.
  5. Задайте Выручке сортировку по убыванию и запустите запрос.
  6. Сверьте пять строк с эталоном, разложив суммы по заказам (см. «Ожидаемый результат»).
  7. Сохраните запрос как qry_ВыручкаПоКатегориям.
Ожидаемый результат

Проверка лидера по строкам: 189.90 (O-10001) + 259.80 (O-10004, 2 × 129.90) + 189.90 (O-10008) + 129.90 (O-10012) = 769.50. Если health_beauty показывает 721.40 — потерян фильтр canceled (лишние 89.90 от O-10006).

  • Фильтр canceled применён в WHERE (до группировки), а не в HAVING.

Подсказка

Если запрос отказывается запускаться с сообщением про «часть агрегатной функции» — какое-то поле осталось без роли в строке «Групповая операция». И помните: в ORDER BY псевдоним «Выручка» недопустим, повторяйте выражение SUM(...) целиком.

Показать эталонное решение

В конструкторе: четыре таблицы, CategoryNameEn, поле «Выручка: Round([UnitPrice]*[Quantity],2)», Σ → Sum, OrderStatus с «Условие» и значением без canceled, сортировка по убыванию. SQL запроса:

SELECT c.CategoryNameEn,
       ROUND(SUM(od.UnitPrice * od.Quantity), 2) AS Выручка
FROM Categories AS c
INNER JOIN (Products AS p
            INNER JOIN (Orders AS o
                        INNER JOIN OrderDetails AS od
                        ON o.OrderID = od.OrderID)
            ON p.ProductID = od.ProductID)
ON c.CategoryID = p.CategoryID
WHERE o.OrderStatus <> "canceled"
GROUP BY c.CategoryNameEn
ORDER BY SUM(od.UnitPrice * od.Quantity) DESC;

Вынесите OrderStatus, задайте «Условие», введите условие без canceled, снимите флажок вывода. Сортировка Выручки — по убыванию. SQL:

SELECT c.CategoryNameEn,
       ROUND(SUM(od.UnitPrice * od.Quantity), 2) AS Выручка
FROM Categories AS c
INNER JOIN (Products AS p
            INNER JOIN (Orders AS o
                        INNER JOIN OrderDetails AS od
                        ON o.OrderID = od.OrderID)
            ON p.ProductID = od.ProductID)
ON c.CategoryID = p.CategoryID
WHERE o.OrderStatus <> "canceled"
GROUP BY c.CategoryNameEn
ORDER BY SUM(od.UnitPrice * od.Quantity) DESC;

Контроль: 5 строк — 769.50, 746.50, 640.00, 631.50, 238.00; итого 3025.50. Разложение лидера: 189.90 + 259.80 + 189.90 + 129.90 = 769.50. HAVING-вариант из чек-листа (пункт 3) отличается одной строкой — категория с выручкой больше 650 отбирается после группировки, результат: bed_bath_table 769.50, computers_accessories 746.50, furniture_decor 640.00:

SELECT c.CategoryNameEn,
       ROUND(SUM(od.UnitPrice * od.Quantity), 2) AS Выручка
FROM Categories AS c
INNER JOIN (Products AS p
            INNER JOIN (Orders AS o
                        INNER JOIN OrderDetails AS od
                        ON o.OrderID = od.OrderID)
            ON p.ProductID = od.ProductID)
ON c.CategoryID = p.CategoryID
WHERE o.OrderStatus <> "canceled"
GROUP BY c.CategoryNameEn
HAVING SUM(od.UnitPrice * od.Quantity) > 650
ORDER BY SUM(od.UnitPrice * od.Quantity) DESC;

Часть 3. Перекрёстные запросы (I02, чек-лист, пункты 5–6). Мастер (Создание → Мастер запросов → Перекрёстные запросы) на таблице Orders: строка — OrderDate по месяцам, столбец — OrderStatus, значение — Count(OrderID). В конструкторе то же получается типом «Перекрёстный» и даёт полный контроль над SQL, включая IN и «Всего»:

TRANSFORM Count(Orders.OrderID) AS Колво
SELECT Format(Orders.OrderDate, "yyyy-mm") AS Месяц,
       Count(Orders.OrderID) AS Всего
FROM Orders
GROUP BY Format(Orders.OrderDate, "yyyy-mm")
PIVOT Orders.OrderStatus IN ("delivered", "canceled", "shipped");

Контроль: 12 строк; delivered = 1 в 9 месяцах, canceled = 1 в 2017-11, shipped = 1 в 2017-10; строка 2018-04 с пустыми статусными ячейками и «Всего» = 1 — это processing-заказ O-10010, у которого нет колонки из-за IN. Вариант с перекрёстной матрицей выручки из сценария — TRANSFORM SUM, столбцы FORMAT(o.OrderDate,"yyyy-mm") IN (шесть месяцев 2018), столбец «Итого» — разобран в секции SQL, его результат совпадает с таблицей из раздела «Ожидаемый результат».

Часть 4. Action-связка (S05, чек-лист, пункты 7–9). Порядок строгий: проверка → копия → обновление → проверки → откат.

SELECT p.ProductID, p.ProductName, p.UnitPrice
FROM Products AS p INNER JOIN Categories AS c
     ON p.CategoryID = c.CategoryID
WHERE c.CategoryName = "automotivo";

SELECT p.* INTO Products_Backup
FROM Products AS p;

UPDATE Products INNER JOIN Categories
ON Products.CategoryID = Categories.CategoryID
SET Products.UnitPrice = ROUND([Products].[UnitPrice] * 1.05, 2)
WHERE Categories.CategoryName = "automotivo";

SELECT ProductID, ProductName, UnitPrice
FROM Products
WHERE ProductID = "P-5001";

SELECT SUM(UnitPrice) AS СуммаЦен FROM Products;

Числа протокола: проверка — 1 строка (P-5001, 119.00); копия — предупреждение «вставить 8 запис(ей) в новую таблицу»; повторная копия — ошибка «таблица уже существует»; UPDATE — предупреждение «обновить 1 запись(и)»; после — P-5001 = 124.95, сумма цен 1429.15 против 1423.20 до. Откат:

UPDATE Products INNER JOIN Products_Backup
ON Products.ProductID = Products_Backup.ProductID
SET Products.UnitPrice = [Products_Backup].[UnitPrice];

После отката: P-5001 = 119.00, сумма 1423.20. Напоминание из задания: второй UPDATE без отката дал бы 124.95 × 1.05 = 131.20 — поэтому число в предупреждении «Будет изменено N строк» проверяется перед каждым запуском. Необязательное архивирование (SELECT INTO Orders_2017_Archive — 6 записей, INSERT INTO … SELECT для O-10010 — +1 запись, DELETE canceled-заказа — 1 запись из Orders и 1 из OrderDetails по каскаду) выполняйте только на копии базы, как разобрано в решении S05.

Краткое резюме

Вы прошли весь аналитический арсенал запросов Access. Кнопка Σ и GROUP BY схлопывают 15 позиций OrderDetails в 5 категорий с проверенными суммами (769.50 у лидера bed_bath_table, итог 3025.50); ROUND оставляет деньги двухзначными, а чёткое разделение WHERE и HAVING спасает от ошибок «часть агрегатной функции». Параметры [Введите начальную дату] с явным PARAMETERS DateTime (и ссылки Forms!frm_Панель!НачальнаяДата на будущее) превращают один запрос в инструмент любого периода. Перекрёстные запросы TRANSFORM … PIVOT дают матрицы вида «категория × месяц», а IN (...) фиксирует их столбцы. Action-запросы SELECT INTO, UPDATE, INSERT INTO … SELECT и DELETE меняют базу необратимо — дисциплина «проверочный SELECT → копия → выполнение с чтением предупреждения „Будет изменено N строк“ → контроль → откат» теперь ваш протокол по умолчанию.
